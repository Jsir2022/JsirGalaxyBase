# 银河职业、贡献与跨服任务平台

日期：2026-09-08
状态：Q.0-Q.3 自动基线完成；Q.4 主要检测链已实现、等待完整影子对照；Q.6 玩家中心和主要编辑闭环已完成，正在实施成熟编辑工具；尚未达到替代 BQ 的生产切换门槛

## 产品结论

职业、贡献和公共任务是银河终端的核心玩法。银行、市场、地产和仓储是其结算、资产与变现设施，
不反过来定义核心玩法。

长期目标是由 Base 自身提供任务定义、编辑、检测、进度、队伍共享、完成和奖励能力，以 PostgreSQL
作为跨服权威真源，以 UI2 终端作为正式玩家与管理员入口。BetterQuesting 只作为成熟语义、算法和
GTNH 既有内容的迁移来源；不搬运其 GUI、网络协议、文件存储单例、Mod 启动代码和全局 Hook。

这不是 BetterQuesting 换皮。终端展示、跨服任务运行时、职业成长与贡献账本均由 Base 持有。

## 已确认的现网与源码基线

- 当前 GTNH 实例使用 `BetterQuesting-3.7.15-GTNH.jar`。
- 固定参考提交：`524b365211b6b3a9672cab8ae45b4e07e726d49e`，主体许可证为 MIT。
- BQ 将任务定义、玩家进度、队伍、生命和名称分别保存；玩家进度已经按 UUID 分文件。
- 现场 S1 有 40 个玩家进度文件，S2 有 29 个；同名文件内容与尺寸存在差异，不能把任一服文件视为跨服真源。
- `QuestInstance` 的原始领取流程先执行奖励、后标记 claimed；该顺序不能直接用于跨服或崩溃恢复。
- BQ Standard 内建检测覆盖物品、流体、合成、方块破坏、击杀、实体/物品交互、位置、会面、计分板、
  XP 和复选确认；奖励覆盖物品、XP、命令、计分板、任务完成和选择奖励。
- GTNH 可能通过其他扩展注册额外 Task/Reward；导入前必须基于完整运行时注册表和任务库生成兼容矩阵。

## 吸收边界

### 吸收并内部化

- 稳定 UUID、任务线、前置关系、可见性和 AND/OR 逻辑。
- Task/Reward 注册表、工厂、配置序列化和未知类型占位。
- 检测与提交算法、物品/NBT/OreDict 匹配、队伍参与者展开。

- 任务编辑、复制、校验、导入导出和版本升级能力。
- GTNH 任务文本、图标、依赖及已有玩家进度的单向迁移。

### 不吸收

- BetterQuesting GUI、任务书物品和快捷键入口。
- BetterQuesting 网络消息与客户端权威动作。
- `QuestDatabase.INSTANCE` 等全局内存真源。
- `SaveLoadHandler` JSON 文件持久化。
- 未经数据库幂等保护的直接奖励执行顺序。
- 与目标无关的硬核生命、书签、主题和命令方块启动设施。

## 目标分层

1. `galaxy-quest-core`：纯 Java 8 定义、状态机、编辑校验、事实规约、进度与奖励资格。
2. `quest-minecraft-adapter`：Forge 事件、物品/流体/方块/实体检测和服务器身份。
3. `quest-postgres`：任务定义、事实收件箱、进度、完成、奖励资格、交付与恢复。
4. `quest-bq-importer`：读取 BQ NBT-JSON、类型映射、未知类型报告和玩家进度迁移。
5. `terminal-career`：职业、贡献、任务、公共任务和编辑器 UI2 页面。

核心不引用 Minecraft、Forge、BetterQuesting 类或其网络对象。平台适配器把游戏事件转换为带稳定事件键的
事实；数据库事务锁定玩家/参与主体进度后归约事实。完成只生成唯一奖励资格，奖励交付是另一条可恢复流程。

## 数据权威原则

- 任务定义按 `quest_id + version` 不可变发布；草稿可以编辑，发布版本不可原地覆盖。
- 事实按 `source_server + event_id` 唯一去重。
- 任务完成按 `participant + quest_id + version` 唯一。
- 奖励资格按 `participant + quest_id + version + reward_key` 唯一。
- 执行奖励前先持久化资格和交付尝试；成功、失败、重试均可审计。
- 客户端只提交意图，不提交玩家 UUID、完成状态、贡献数量或奖励结果。
- 职业、贡献与任务分表：任务产生事实和完成，贡献是追加账本，职业由版本化规则解释长期成长。

## “完成 BQ 替代”的验收定义

只有同时满足以下条件，目标才算完成，而不是以某个类、页面或测试批次完成来缩小终点：

1. GTNH 当前任务库使用的所有 Task/Reward 都通过运行时兼容矩阵与影子对照，重要 BQ Standard 类型也有
   明确的 `SUPPORTED` 或有理由的拒绝状态。
2. 终端覆盖玩家浏览、详情、追踪、手工提交、Choice、领取，以及管理员任务/章节创建、编辑、复制、排序、
   校验、发布、退役、导入、诊断和恢复。
3. PostgreSQL 成为跨服定义、进度、完成、奖励和偏好的唯一权威真源；所有客户端只提交意图和版本绑定。
4. BQ 与 Base 完成不少于约定观察期的并行影子计算，差异已解释、修复或形成明确迁移例外。
5. 定义与玩家进度迁移经过 dry-run、备份、幂等重跑、故障恢复和回滚演练。
6. 灰度链验证完成后冻结 BQ 写入与领取，终端成为唯一正式入口；确认无需回退后才移除运行依赖并保留只读
   备份与迁移审计。

Q.1 自动基线已经包含 PLAYER/PARTY/TEAM/PUBLIC 参与主体、成员事实归属、重复周期、周期化奖励资格、
稳定事实键、Task evaluator 注册表、事实投影、事务仓储端口及定义图校验。

Q.2 已建立独立 `galaxy-quest-bq-importer`，只读解析 BQ 的带类型后缀 NBT-JSON，完整保留 Task/Reward
原始配置，并能导入玩家完成、领取、时间戳、Task 完成用户与数值进度。数值进度兼容 BQ 的两种现存
编码：检索/合成/流体/方块破坏的 `data` 整数数组，以及击杀任务的 `value` 整数；原始 Task JSON 仍会
保留，避免迁移过程中丢掉当前未结构化的字段。对 S2 当前 DefaultQuests 的实跑结果为：

- 任务 3744 个；
- Task 共 9 种：retrieval 3863、optional_retrieval 1267、checkbox 203、crafting 133、hunt 104、
  location 33、fluid 15、block_break 1、meeting 1；
- Reward 共 4 种：item 4181、choice 957、questcompletion 308、xp 2；
- 当前任务库没有出现第三方自定义 Task/Reward ID，兼容面比预期更集中，兼容报告的 unknown 集合为空。

对 S2 的 29 个只读玩家进度文件实跑：共解析 108557 个任务进度、4524 个已完成状态、1279 个已领取
状态；所有 Task 都属于上述 9 种类型。该数据只用于验证数据形状，不作为权威合并结果，也未写回现场文件。

定义归一化不再使用早期的统一 `target=1` 占位：检索、可选检索、合成、流体和方块破坏均保留逐项
目标和向量进度；击杀保留实体、数量、伤害类型、子类与 NBT 条件；位置和会面保留维度、坐标、范围、
可见性、反向、实体数量与 NBT 条件；选择奖励明确要求玩家选择，XP 明确区分等级与经验点。纯 Java
`TaskProgress` 已支持不可变向量、逐项完成判断和单调合并，形状变化会产生显式迁移错误而非静默压平。

兼容状态目前统一为 `ADAPTED`，表示定义和旧进度已经可无损转换，但 Minecraft 事件检测器与奖励交付器
仍在 Q.4/Q.3 实现；只有完成运行时实现和影子对照后才会升级为 `SUPPORTED`。

Q.3 已新增独立 `galaxy-quest-postgres` 模块和第一版 DDL，覆盖不可变定义版本、事实收件箱、参与主体进度、
向量 Task 进度及奖励资格。所有事实、进度和资格写入必须位于同一个 `JdbcQuestTransaction`；进度身份使用
事务级 advisory lock，即使数据库中尚无进度行，并发的不同事实也不会在首次写入时发生丢失更新。

核心层新增 `QuestRuntimeService`，一次事实在同一事务中投影到全部相关任务、归约进度并生成奖励资格；
重复事实直接返回 duplicate，不再依赖调用方自行拼装正确顺序。真实 PostgreSQL 临时数据库测试已经覆盖：

- 同一事实重复提交只接受一次；
- 两个并发事实更新首次出现的同一任务时最终进度为 2，无丢失更新；
- 并发相同事实只创建一条事实和一组奖励资格；
- 强制异常会同时回滚事实、进度和奖励资格；
- 向量进度写入并读取后保持逐项值和目标。

Q.3 第二批补齐了任务定义草稿、内容哈希乐观锁、不可变发布与退役生命周期；奖励资格采用
`PENDING -> DELIVERING -> DELIVERED / FAILED / ABANDONED` 状态机，通过 `FOR UPDATE SKIP LOCKED`
租约、交付尝试表、过期租约接管和陈旧确认拒绝支持多服工作器。实际物品、经验和命令交付端必须把
`entitlement_key` 作为外部幂等键，因此即使外部交付成功后数据库确认前崩溃，恢复调用也不能重复发奖。

真实 PostgreSQL 临时库进一步验证了草稿冲突、发布后不可变、失败延迟重试、陈旧工作器拒绝、过期租约
接管和尝试审计；临时数据库与角色均已删除。新增 BQ 双源只读冲突分析器，按玩家和任务将记录分类为
`IDENTICAL / LEFT_ONLY / RIGHT_ONLY / LEFT_AHEAD / RIGHT_AHEAD / DIVERGENT`。比较只承认完成、领取和逐项
数值的单调领先；交叉领先、Task 类型变化和向量形状变化一律标为冲突，不擅自合并。由于 S1 操作边界，
本轮只完成工具和确定性测试，没有读取 S1 现场目录。

Q.4 第一批已按 BQ 源码的真实分工实现：击杀、合成、熔炼和铁砧由 Forge 服务端事件捕获，复选确认由
服务端绑定任务键的意图转成事实。事件处理器不遍历任务、不直接改进度，只生成带进程启动 ID 与单调序号
的 `GameplayFact` 交给事务 Sink。合成保留 BQ 对 Shift-click 空结果栈重新求配方数量的修正；熔炼保留
最小数量修正；客户端世界、FakePlayer、取消事件和无玩家伤害源均被拒绝。

核心新增 BQ 兼容求值器：击杀支持精确实体、服务端派生的父类型别名和伤害类型；合成使用逐项向量、
注册名/meta/通配 meta/OreDict，并尊重 craft/smelt/anvil 开关；复选必须匹配服务端目标 Task key。NBT 字段
已经保留在事实合同中；物品消费端已完成 BQ 的完整/部分 NBT 比较，其他事实求值器仍待统一采用该合同，
因此非忽略 NBT 的整体兼容状态暂时仍为 `ADAPTED`。
导入器同时为三类定义写入稳定 fact type。该批只建立适配与求值合同，尚未注册 Forge Handler，避免在
定义目录、成员解析和生产 migration 未接好时产生无法消费的事实。

下一步继续 Q.4：补齐会面检测与消费型提交协议，然后实现实际物品、经验、命令、任务完成和选择奖励
交付端。库存检索必须采用“权威快照”而不是累计事件，消费型提交必须具备事务预约/确认，不能用简单计数
模拟。DDL 仍未接入生产 migration，运行时也尚未注册到 Mod 启动流程。

Q.4 第二批已经补齐运行计划链：PostgreSQL 可列出每个任务 UUID 的最新发布版本并查询指定参与主体已完成的
前置任务；`QuestEvaluationPlanner` 在事实事务内部解析定义、成员和前置状态，只选择声明接收该 fact type
的任务。Assignment Policy 明确控制一个定义归属 PLAYER/PARTY/TEAM/PUBLIC 中哪一层，当前 BQ 导入默认
仅推进 PLAYER，绝不会因为玩家同时属于多个范围而重复推进。没有相关任务的事实返回 `IGNORED` 且不写
事实收件箱。

方块破坏已按 BQ 语义实现为逐项向量，并保持“一次破坏只推进第一个匹配需求”；支持注册名、meta、通配
meta 与 OreDict。非消费型检索采用权威库存快照：未完成时数量可随背包减少而回落，达到完成后锁定；同一
物品栈按需求顺序分配，不能同时满足多个要求。玩家库存事实目前按服务端每秒快照生成，但 Handler 仍未
正式注册。消费型 retrieval 明确不接受该快照求值器，留待预约、扣除、确认一体化协议。

Q.4 第三批补齐非消费型流体库存快照和地点检测。流体以毫桶为单位按需求顺序分配，同一容器内容不能
重复满足多个要求；消费型 fluid 与 retrieval 一样拒绝快照捷径。地点检测对齐 BQ 的维度、三维欧氏/曼哈顿
距离、范围、生物群系和 invert 语义。结构存在性和目标可见性属于平台派生证据：事实缺少相应证据时任务
保持原状，尤其禁止 inverted 任务因为“适配器没提供证据”而被误完成。当前基础周期事实只提供服务端坐标、
维度和生物群系，结构/视线证据将在定义感知的探针中补齐。事件处理器仍未注册。

Q.4 第四批补齐 meeting：一次权威附近实体快照保留实体 ID、服务端派生父类型别名和可选 NBT，求值器
支持精确类型/子类型、数量和扫描半径完整性校验。扫描事实必须声明 `observedRadius`；小于任务要求范围的
快照直接视为证据不足，不能用“没扫到”冒充“附近不存在”。`QuestObservationPlan` 从最新已发布定义汇总
是否需要库存、流体、地点观察及最大的会面半径，Handler 只在 BQ 对应的 20/60/100 tick 周期生成必要事实，
避免每个任务分别扫描。至此现网 9 种 BQ Task 都有明确 fact type 和核心求值器，但消费任务、部分 NBT、
地点结构/视线证据仍是适配态，尚不能宣告完全替代 BQ。

Q.4 第五批建立消费型任务的跨服 Saga。BQ 原版在检测或手工提交时直接扣除玩家库存；Base 将其拆成稳定
提交键对应的 `PREPARED -> APPLIED -> CONFIRMED`，资源不足进入 `REJECTED`。Minecraft 扣除端必须把稳定
提交键和库存变化一同持久化，重试同一键不得再次扣除；随后 `galaxy:consumption_applied` 事实精确绑定玩家、
Quest UUID、定义版本、Task key、资源种类和逐项数量，进度事实与数据库确认处于同一事务。若扣除后崩溃，
数据库中的 APPLIED 状态或玩家持久化证据可以继续确认；若事实已经处理，事实唯一键保证不会重复推进。
PostgreSQL 已加入提交表、内容碰撞拒绝和状态迁移仓储。客户端不得提交物品定义或扣除数量。

服务端规范请求授权器现已完成：外部意图只允许包含稳定提交键、服务器、当前玩家、Quest UUID 和 Task key；
定义版本、资源类型、匹配参数及逐项剩余数量全部从最新发布定义和锁定进度计算。它复用 QuestEngine 的前置、
状态和重复周期判定，拒绝锁定/已完成任务、非消费任务和不属于该 Quest 的 Task。普通提交入口只能接收这种
最小意图；崩溃恢复入口只能按数据库中已存在的提交键继续，调用方不能再构造任意扣除请求。

Q.4 第六批完成玩家背包的物品消费端。服务端只按 UUID 解析当前在线玩家，先对全部需求建立不重复使用
物品栈的完整扣除计划，资源不足或定义异常时不修改背包；匹配覆盖注册名、耐久/通配 meta、OreDict，以及
BQ 的完整/部分 Compound、List、数值和数组 NBT 语义。成功扣除后，SHA-256 化的稳定提交标记与背包通过
世界的玩家数据接口同步写盘；重试先检查标记，持久化抛错则恢复背包与标记。

Q.4 第七批补齐流体容器消费。规划器在背包副本上逐需求、逐容器排空，支持 Forge 固定容器和
`IFluidContainerItem` 可变容器，按名称和可选 NBT 匹配；空容器或部分排空容器必须能安全返回背包，整个
计划才允许提交。BQ 在背包满时把空容器掉落到世界，Base 为保证崩溃回滚和跨服幂等，改为拒绝本次提交，
避免产生无法与玩家 NBT 同事务恢复的掉落实体。Forge 流体 API 已隔离为可注入 adapter，纯 JUnit 可验证
分配、部分排空、输入不变和满背包拒绝，不依赖完整游戏 Bootstrap。在运行时装配、奖励交付和生产 migration
完成前，Forge Handler 与消费入口继续保持未注册。

Q.3 奖励恢复链的第二批新增精确类型路由和选择奖励门禁。`RewardDeliveryRouter` 只把租约交给注册了相同
type ID 的 handler，未知类型不可重试并进入隔离，不能静默领取。`bq_standard:choice` entitlement 在数据库
没有玩家选择时不会被 worker 租走；选择操作同时校验 entitlement 属于服务端当前玩家、仍可交付、类型正确
且索引位于定义的 `item.count` 内。第一次选择不可变，重复相同选择幂等，不同选择返回冲突；租约携带由
数据库注入的 `choice.index`，客户端不能伪造。下一批据此实现 item/choice、XP 和 quest-completion 的实际
handler 与玩家 NBT/数据库幂等交付。

Q.4 第八批完成首组真实玩家奖励 handler。`bq_standard:item` 与 `bq_standard:choice` 共用服务端物品交付器，
从导入后的规范参数恢复 ItemStack、meta、数量和完整 NBT；choice 只读取租约中由数据库注入的
`choice.index`。NBT 字符串递归替换 `VAR_NAME/VAR_UUID`，与 BQ 行为一致。所有物品先在背包副本中完成合并
与空槽分配，确认可容纳后才修改玩家；背包满返回可重试失败，不采用 BQ 的世界掉落，以免掉落实体无法与
数据库确认共同回滚。稳定 entitlement key 的 SHA-256 标记和背包由同一次玩家数据 flush 持久化，保存失败
恢复背包和标记。

XP handler 精确复刻 BQ 1.7.10 的等级累计经验曲线和经验条换算；`xpUnit=levels` 时增加该等级从零累计所需
经验点，`points` 时直接增加点数。经验字段与幂等标记同样先持久化，失败恢复，成功后才同步客户端经验条。
当前只接受 PLAYER entitlement；PARTY/TEAM/PUBLIC 的奖励分配策略尚未定稿，明确返回不可交付而不是默认发给
触发者。该批结束时 handler 仍未装配进 Mod 生命周期，quest-completion 奖励尚待下一批，因此生产环境未启用。

Q.4 第九批实现 `bq_standard:questcompletion`。BQ 原版直接修改全局 QuestDatabase 中目标任务的完成状态；
Base 改为 `QuestCompletionRewardPort`，在同一 PostgreSQL 事务中锁定参与主体的目标进度、读取最新发布定义、
写入目标任务完成状态并创建目标任务的全部奖励资格。强制完成不检查目标前置，与 BQ 的奖励语义一致；为使
数据库投影自洽，目标 Task 的各分量同时写至目标值。目标已经完成时作为幂等成功，不重复生成资格；目标不
存在或未发布则永久失败，数据库异常交由通用 worker 重试。即使完成事务后、来源 entitlement 确认前崩溃，
重试也只会读到已经完成，稳定 entitlement key 仍不会重复发出目标奖励。循环完成奖励会因完成状态收敛。

至此当前任务库出现的四种 BQ Reward 均已有明确交付实现或数据库门禁：item、choice、xp、questcompletion。
它们尚未装配进 Mod 生命周期；PARTY/TEAM/PUBLIC 的物品与经验分配策略、运行时启动/停止、生产 migration、
影子运行和终端任务应用仍是后续阶段。

Q.4 第十批把兼容边界从“当前任务库出现的类型”扩到完整 BQ Standard 重要类型。导入器新增
`interact_entity`、`interact_item`、`scoreboard`、Task XP，以及 command、scoreboard Reward；它们的原始
带类型 NBT-JSON 和标量设置不会在导入时丢失。交互任务映射为服务端交互事实，保留命中/右键、目标实体、
目标物品、目标方块及 NBT 配置；计分板保留目标、比较运算、criteria、显示名、单位换算和后缀；XP Task
把等级阈值按 BQ 曲线规范化为经验点，并保留是否消费。

这里新增的是无损定义合同和稳定 fact type，不等于运行时已支持：交互事件捕获、计分板/XP 权威观察、XP
消费 Saga、命令白名单及计分板幂等奖励仍需逐个实现。在这些 handler 和自动测试完成前，新增六类继续标记
为 `ADAPTED`，不能因为导入器认识 type ID 就宣称 `SUPPORTED`。

Q.4 第十一批补上非消费 XP、计分板和基础交互运行语义。`QuestObservationPlan` 现在只为发布定义实际需要的
XP 与计分板目标建立探针：计分板沿用 BQ 每 20 tick、XP 沿用每 60 tick 的频率；缺失计分板目标时按 BQ
criteria 创建，事实只携带服务端读数。计分板求值覆盖 `= / < / > / <= / >= / !=` 六种操作并在完成后锁定；
非消费 XP 使用绝对经验点快照，完成前允许随玩家经验消耗而回落；`consume=true` 明确拒绝快照捷径。

Forge 交互捕获覆盖左击/右击方块、攻击/交互实体，事实保存动作、实体父类型别名、手持物、方块、OreDict、
meta 和可用 NBT。基础 evaluator 已覆盖动作开关、实体子类型、手持物和方块匹配。带 NBT 条件的交互任务仍
保守不推进，直到统一的跨模块 canonical NBT matcher 完成；这避免把“尚未实现比较”错误解释成匹配成功。

Q.4 第十二批完成 canonical NBT 边界。纯 Java `PortableNbt` 使用稳定、可逆的类型树编码，BQ 带类型后缀
JSON 与 Minecraft 1.7.10 `NBTBase` 分别在适配层转换，核心求值器不依赖 Gson 或 Minecraft。匹配语义覆盖
跨数值宽度相等、Compound 部分匹配、List/byte[]/int[] 无序且不重复占用，以及畸形外部编码 fail-closed。
crafting、retrieval、fluid、block break、hunt、meeting 与两类 interaction 已统一使用该合同；原始 JSON/NBT
文本继续保留给奖励重建和来源审计。至此此前“带 NBT 条件交互保守不推进”的限制已解除，但生产 Handler
仍保持未注册，下一步先为消费型 XP 设计可表达 BQ 增量扣除量的 Saga 结果合同，再处理命令与计分板奖励。

Q.4 第十三批将消费 Saga 从“请求量即扣除量”升级为持久化实际扣除向量。`ConsumptionApplyResult`、提交仓储
和确认事实均携带 `appliedAmounts`；PostgreSQL 的 `applied_values` 在 APPLIED 状态落库，进程崩溃后仍按
同一向量推进。物品/流体保持全额原子扣除，消费型 XP 则按 `min(剩余目标, 玩家现有经验)` 增量扣除，玩家
NBT marker 同时保存实际量，重试不会二次扣除。该设计对齐 BQ `TaskXP.detect`，而不是要求玩家一次攒够全部
经验。临时真 PostgreSQL 已验证结构、状态迁移和恢复后删除；生产 DDL 尚未应用，运行入口仍默认关闭。

Q.4 第十四批处理最后两种 BQ Standard Reward。计分板奖励不直接重放“相对增加”：首次交付先根据当前分数
计算绝对目标并写入玩家持久 marker，flush 成功后才幂等 `setScorePoints`；租约或进程崩溃后的重试读取同一
目标，因此不会重复加分。绝对设置、只读 objective、criteria 回退和 int 饱和均有明确行为。

命令奖励保留 `VAR_NAME/VAR_UUID` 与 `viaPlayer` 参数，但不复制 BQ 的任意管理员命令调度器。纯核心新增显式
command-root allowlist 和 `CommandRewardExecutor`，后者必须用 entitlement key 做持久幂等；控制字符、超长、
未允许命令永久拒绝。当前 GTNH 默认任务库未发现 command reward，因此默认空白名单不会阻断现有内容；未来
只有 Base 自己提供幂等业务适配器后才开放对应根命令，不能把 `/give` 等非幂等命令直接加入生产白名单。

Q.6 第一批开始吸收 BQ 的编辑语义，但不吸收它的编辑 GUI、Packet 或 `QuestDatabase.INSTANCE`。纯 Java
`QuestDraftEditor` 以语义操作编辑名称、说明、两类逻辑、重复规则、前置、Task 与 Reward；支持稳定 key 的
增删、替换和排序，并始终构造新的不可变 `QuestDefinition`。发布版本不会被原地修改，后续终端与管理命令
必须调用这些操作和服务端校验，而不能提交完整的“最终任务状态”覆盖数据库。

BQ `QuestLine/QuestLineEntry` 的重要部分被重新表达为 `QuestChapterDefinition/QuestChapterEntry`：章节只负责
名称、资源引用和任务位置，不拥有玩家进度。章节有独立草稿编辑器、内容哈希、乐观锁以及
`DRAFT -> PUBLISHED -> RETIRED` 生命周期；PostgreSQL 新增版本化章节定义表。章节内允许视觉重叠，命中时按
后放置条目优先，与自由布局编辑器兼容；同一 Quest 在一个章节内不能重复放置。

只读 BQ 导入器已覆盖 GTNH 的 split DefaultQuests 格式：从 `QuestLinesOrder.txt` 读取章节 UUID、显示顺序和
名称，从每个目录的 `QuestLine.json` 读取说明、图标、背景和声明 UUID，从其余 JSON 读取 Quest UUID、x/y
和尺寸。URL-safe Base64 中可能出现连字符，目录解析不得简单取最后一个 `-`。对当前客户端快照实跑得到
3739 个 Quest、46 个章节和 3842 个位置，所有类型均可识别；原始 BQ 仍不成为运行时依赖或跨服真源。
Q.4/Q.6 行为批次已补齐 Quest 的可见性、图标引用、main/silent、locked progress、simultaneous、
auto-claim、global/globalShare 和更新/完成音效。默认锁定任务不再接受进度；显式 locked progress 可以在
锁定期间推进；simultaneous 未整体满足时会清除局部完成；非相对重复按 epoch 边界判断。可见性由纯 Java
求值器解释 HIDDEN/SECRET/UNLOCKED/NORMAL/COMPLETED/CHAIN/ALWAYS，不把 BQ 客户端数据库带入运行时。

奖励资格现在区分 `CLAIMABLE` 与可投递的 `PENDING`：普通任务完成后先等待玩家领取，只有 auto-claim
任务直接进入投递队列。手动选择奖励必须由当前服务端认证玩家先写入不可变 choice，再领取；领取事务只锁定
该玩家、Quest 版本和周期的资格，跨玩家领取、重复领取及未选择领取均有明确状态。一次性 PostgreSQL 真库
测试覆盖了完整领取链并在结束后删除数据库与角色，生产 schema 尚未应用。

编辑器基础新增平台无关 `QuestEditorTypeRegistry`、元素/字段描述和结构化参数校验。BQ 适配层为完整
13 种 Standard Task 与 6 种 Standard Reward 提供字段合同，支持布尔、整数、枚举、UUID、物品/流体/方块
列表、实体、NBT 和命令等编辑控件语义；列表逐项校验身份与正数数量。该层只描述和校验服务端规范参数，
不复刻 BQ GUI、Packet 或裸 JSON 编辑。

Q.6 第二批已建立平台无关玩家任务中心：`QuestCenterVisualDocument` 在 Java2D 与 Minecraft 宿主之间共享，
覆盖章节、全部/进行中/待领取筛选、任务摘要、详情、Task 向量进度、奖励与领取动作。固定场景已经进入三档
视口和三套主题的 99 个终端视觉快照。服务端 `QuestCenterQuery` 只返回当前参与主体可见的最新发布定义、进度
与奖励状态；`QuestCenterPageRequest/QuestCenterPaginator` 在网络前完成搜索、状态筛选、章节与任务分页，并将
客户端页大小分别限制为 12 与 24，避免 46 章节和 3739 任务被客户端静默截断或一次性传输。章节网络模型只
携带完成/总数摘要，不携带整章全部坐标。

Q.6 第三批已把玩家任务中心接入 Base 自己的正式终端协议，而没有引入 BetterQuesting Packet。新增的
`TerminalQuestCenterSectionSnapshot` 是有界、无 Minecraft 类型且不含玩家身份的线 DTO；客户端动作只携带
章节、任务、筛选、查询词和页码。服务端在处理当前连接的 `EntityPlayerMP` 后才构造 `ParticipantId`，客户端
无法提交账户 UUID、完成状态或奖励结果。章节、任务、Task 和 Reward 在编码端分别限制为 12、24、64、64，
畸形数量在解码端 fail-closed；详情刷新会保留详情视图，返回动作才退出详情。

`TerminalPageRegistry` 的职业入口现在使用共享 `QuestCenterVisualDocument`，Minecraft 适配器只负责把纯
`VisualItem` 解析为真实 `ItemStack`，查询、筛选、章节/任务分页、详情和领取意图都走现有 Base
`TerminalActionMessage`。当前生产运行时仍未安装 `QuestCenterQuery`，因此正式环境会显示明确不可用态且不会
碰现有 BQ。

Q.6 第四批增加默认关闭的 `QuestModule` 组合根。服务端配置 `questPostgresReadEnabled=false` 是硬默认；只有
专用服务器、Institution Core 已准备共享 JDBC、并且五张 Quest 读取表通过只读 `to_regclass` 校验时，模块才会
向终端安装 `JdbcQuestCenterQuery`。它不会自动执行 DDL，也不会持有第二套数据库凭据。客户端配置中的 quest
分类会被移除，避免把服务端开关或数据库能力暴露为客户端选项。Quest Core 与 Quest PostgreSQL 已内嵌进 Base
最终 JAR，并由自包含门禁确认，因此玩家无需安装额外 Mod 或库。

领取链也已从占位升级为服务端真实合同：`AuthenticatedQuestClaimService` 只接受当前认证玩家与 Quest UUID，
在事务内从最新发布定义和该玩家进度推导 definition version 与 cycle，再调用幂等 Claim Repository；客户端
不能指定版本、周期或他人身份。领取成功只把资格转为 `PENDING` 交付队列，缺少 Choice、重复领取、非本人、
非法状态和未找到都有独立反馈。当前生产开关仍关闭且 schema 未迁移，所以不会改变现网 BQ 行为。下一步实现
Choice 奖励选项的服务端派生 DTO/动作与玩家 UI，再进入管理员草稿编辑/发布页面；Forge 检测 Handler 和生产
migration 仍须等待影子运行门槛。
### Q.6 奖励多选项认证边界（2026-09-10）

已建立 `AuthenticatedRewardChoiceService`。它按认证玩家、最新已发布任务定义和当前进度循环推导稳定 entitlement key，再调用不可变选择仓储；客户端不得提交玩家、版本、循环或 entitlement。下一步是把 BetterQuesting choice 参数映射为有界选项列表，并接入终端详情、协议和纯 Java 视觉场景。

终端闭环现已完成：BetterQuesting `bq_standard:choice` 的 `item.*` 参数映射为最多 32 个选项，选择意图只含任务 ID、稳定奖励键和选项序号；服务端完成身份、发布版本、当前循环和 entitlement 推导。查询模型会返回已锁定选项，UI2 禁止再次改选，原有领取服务仍负责将完整任务奖励推进到交付队列。

### Q.6 跨服任务追踪（2026-09-10）

任务追踪不再保存为客户端 JSON。新增 `galaxy_quest_player_preference` PostgreSQL 真源和认证切换服务；客户端只提交任务 ID，服务端以当前连接玩家作为所有者，并验证任务仍有已发布版本。任务目录和详情会返回追踪状态，UI2 提供星标与追踪/取消追踪动作。查询最多读取最近 32 个追踪任务，避免无界 HUD 或网络负载；下一批在此真源上构建 HUD 摘要，而不是复制 BetterQuesting 的客户端追踪存储。

HUD 摘要已经接入 Base 自有协议。服务端在玩家登录及低频周期生成最多 5 个任务、每个任务最多 3 个目标的只读投影；客户端缓存不可变快照并在无 GUI 的游戏 HUD 左上角显示最多 3 个任务。断开世界后缓存立即清空。该协议不包含玩家身份、任务编辑数据或写权限，也没有搬运 BetterQuesting 的同步包和客户端 JSON。

### Q.6 服务端草稿管理边界（2026-09-11）

纯核心新增 `QuestDraftManagementService`，统一承接草稿创建、基于内容哈希的更新、发布和退役。每个动作先检查服务端认证的 `QuestEditorActor` 权限，再用 `QuestEditorTypeRegistry` 完成元素类型与字段参数校验，最后才进入事务；禁止客户端提交“我是管理员”一类权限标志。重复版本、过期内容哈希和生命周期竞争均收敛为结构化 `CONFLICT`，权限、校验失败和不存在分别返回稳定状态。

该层复用现有不可变 `QuestDefinition`、`QuestDraftEditor` 和 PostgreSQL 仓储，没有引入 BetterQuesting 的客户端全局数据库、编辑 GUI 或 Packet。

管理查询现已拆为独立 `QuestDefinitionManagementQuery`，按生命周期、名称或完整 UUID 搜索，并使用服务端限制为每页最多 50 项；读取所有草稿/历史版本不会污染只提供最新发布版本的玩家运行时目录。`AuthenticatedQuestDefinitionManagementQuery` 在访问数据库前验证权限，Minecraft 适配器从当前在线玩家 UUID 解析真实实体并检查 OP level 2。BQ Standard 的 13 类 Task 与 6 类 Reward 编辑字段规范已下沉纯核心，导入器仅保留兼容门面，生产组合根无需打包导入 CLI 或额外 Gson。

Base 自有终端协议现支持管理列表、筛选、分页、定义详情、发布和退役。定义详情包含说明、逻辑、前置、Task、Reward 与行为选项的有界只读投影；发布必须同时提交服务端先前返回的内容哈希，服务端重新鉴权并执行乐观锁。发布前新增完整依赖图校验：直接前置必须存在已发布版本，依赖图必须可完整读取且不得因为候选版本形成循环。UI2 管理详情已提供发布/退役按钮并纳入三主题三视口视觉门禁。下一步进入草稿创建与真正的字段编辑表单，更新仍必须经过不可变定义、类型注册表和内容哈希校验。

字段编辑的核心命令合同已经开始实施。`QuestDraftEditRequest` 将 1–128 个白名单语义操作组成一次编辑批次，操作只覆盖名称、说明、逻辑、前置、Task 与 Reward 的增删改序；服务端先读取指定 DRAFT 和内容哈希，在内存副本上完整应用并统一执行类型/参数校验，最后只做一次乐观锁写入。任一操作失败不会留下部分修改。Base 自有二进制载荷限制总大小、操作数、参数数和逐字段长度，并拒绝未知操作、重复参数及尾随数据。正式 UI2 已可编辑名称、说明、前置逻辑和目标逻辑；保存成功后以新内容哈希刷新详情。Task/Reward 动态字段表单、前置选择器和创建模板仍属于下一批，客户端不得直接提交序列化 `QuestDefinition`。

Task/Reward 字段表单现由服务器下发的 `QuestElementTypeDescriptor` 生成。管理协议以最多 32 类、每类 32 字段、每字段 32 枚举项的只读目录传递字段 key、显示名、类型、必填、数值上下界和枚举值。编辑器对 BOOLEAN 使用开关、ENUM 使用受限选项，其余结构化类型使用有界文本表示，并将超过四项的字段分页；元素可更改稳定 key、可选属性和参数。DRAFT 详情现在也能按服务端类型目录新增 Task/Reward、上下移动已有元素，并经二次本地确认删除；新增与替换、移动、删除仍分别形成单个白名单语义操作，由服务端统一鉴权、校验和乐观锁提交。前置选择器和创建模板继续在后续批次补齐。

前置任务选择器已进入正式 UI2 草稿编辑器。详情请求在完成同一服务端授权后额外读取最多 50 个最新已发布定义作为候选，排除任务自身；客户端只维护 UUID 集合，保存时按原集合与新集合的差集生成 `ADD_PREREQUISITE/REMOVE_PREREQUISITE`。发布阶段仍会从 PostgreSQL 重新读取完整依赖图并拒绝缺失依赖或循环，因此候选展示不是安全边界。新草稿模板仍是下一项。

新草稿创建不接收客户端构造的 UUID、版本或完整 `QuestDefinition`。终端只提交有界名称和固定模板 ID，服务端 `QuestDraftTemplate` 生成身份、版本、默认逻辑与初始目标，再进入与普通创建相同的权限、类型校验和事务。首批模板为 EMPTY、MANUAL_CHECK、EXPERIENCE；模板产物全部由标准类型注册表自动验证。创建后返回 DRAFT 筛选结果，不引入 BetterQuesting 的编辑网络或客户端数据库。

重复策略与任务行为现通过单个 `SET_OPTION` 白名单语义操作编辑，新增枚举值追加在既有操作序号之后以保持旧二进制载荷兼容。服务端只接受 repeat cooldown/relative、visibility、icon、main、silent、auto-claim、locked progress、simultaneous、global/globalShare 和两种音效键；布尔值严格解析，未知键、非法周期和非法枚举导致整批回滚。UI2 将这些选项分三页以覆盖紧凑窗口，字符串资源仍受 256 字符限制，客户端不提交 `QuestBehavior` 对象。
