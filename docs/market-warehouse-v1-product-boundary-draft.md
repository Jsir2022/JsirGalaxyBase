# 市场仓库 v1 产品边界草案

日期：2026-06-14

这份草案的目标不是直接定义 GUI，而是先把“市场里的仓库”到底是什么、应该服务什么制度、又不应该被误做成什么，先钉清楚。

当前判断：

- `仓库` 不只是一个可视化容器页
- 它首先是 `资产状态系统`
- 然后才是玩家在终端里看到的 `仓库工作台`

这份文档主要面向：

- 标准商品市场
- 后续企业化经营
- 公共工程 / 公共财政
- 跨服流通与制度扩展

## 1. 为什么现在必须单独定义仓库

当前市场系统已经不是单纯的买卖页面，而是在长成一套完整制度链：

- 生产
- 入库
- 挂单
- 撮合
- 结算
- 提取
- 恢复
- 审计

如果不先定义仓库边界，后面很容易出现三种跑偏：

- 把市场仓库做成“万能大箱子”
- 把三类市场重新混回同一套库存模型
- 为了 UI 方便，反过来破坏资产状态和制度边界

所以第一原则是：

- `仓库先是制度模型，后是页面`

## 2. 当前对“仓库”的正式理解

在 `JsirGalaxyBase` 里，仓库不应先理解成玩家家里的储物箱，而应理解成：

- 一套被制度定义的 `受监管资产池`
- 一套为交易、交付、结算和公共消耗服务的 `状态化库存系统`

它的核心职责不是“放东西”，而是：

- 记录资产当前属于什么制度状态
- 记录资产当前归谁控制
- 记录资产当前能做什么、不能做什么
- 让后续市场、企业、公共工程、跨服物流都能在同一套规则下工作

## 3. 现实模型映射

为了后续玩法更稳，建议把现实里的三种仓储角色映射进来，而不是一开始做一个混合大仓。

### 3.1 市场托管仓

对应现实中的：

- 交易所托管仓
- 平台履约仓
- 受监管的交割仓

它的特点是：

- 资产进入后，不再等同于玩家背包里的自由物品
- 能否卖出、能否撤回、能否领取，都由制度状态决定
- 重点不是装饰性仓储，而是交易可靠性与结算一致性

这类仓库最适合作为当前第一阶段主链。

### 3.2 企业私有仓

对应现实中的：

- 玩家创办企业的原料仓
- 成品仓
- 中转仓
- 运营库存

它的特点是：

- 服务于企业经营，而不是直接服务于市场撮合
- 更关注采购、生产、备货、调拨、销售节奏
- 可以与市场仓发生流转，但不应直接等同于市场托管仓

这条线很适合作为后续企业玩法的核心资源基础。

### 3.3 公共仓 / 政府储备仓

对应现实中的：

- 公共工程物资储备
- 政府收储
- 战略储备
- 福利与救济物资池

它的特点是：

- 资产用途由公共制度决定，而不是由个体盈利最大化决定
- 可能关联公共订单、基建、福利发放、价格稳定、紧急调度
- 它也可以从市场采购，但自身不应该退化成普通玩家私仓

这条线很适合未来和公共任务、公共工程、贡献度、声望体系挂接。

## 4. v1 要先做成什么，不做成什么

### 4.1 v1 正式目标

`市场仓库 v1` 先只做：

- 标准商品市场的正式托管仓
- 面向真实交易闭环的资产状态系统
- 可审计、可恢复、可解释的库存状态

它应回答五个问题：

1. 玩家当前有哪些 `可交易库存`
2. 哪些库存已经被 `挂单占用`
3. 哪些资产已经成交但仍 `待领取`
4. 哪些资产处于 `异常 / 待恢复`
5. 最近这批资产发生了什么操作

### 4.2 v1 明确不做

v1 不应被做成下面这些东西：

- 普通大箱子 GUI
- 企业经营总仓
- 公共财政总仓
- 跨服全物流系统
- 三类市场共用的一套万能库存模型
- 所有物品都能直接塞入的无边界仓库

## 5. 标准商品市场里的仓库正式边界

当前最稳的边界是：

- 仓库只服务 `标准商品市场`
- 只接收 `已通过正式目录准入` 的标准商品
- 只围绕标准商品的交易与交割状态工作

它至少应具备这些状态：

- `AVAILABLE`
  - 已入市场仓，可继续卖出或参与后续动作
- `ESCROW`
  - 因挂卖、履约或制度动作被占用，暂不可自由处理
- `CLAIMABLE`
  - 已成交但尚未提取到玩家侧
- `EXCEPTION`
  - 发生中断、异常或恢复待处理

这里最关键的原则是：

- `市场仓 != 玩家背包`
- `市场仓 != 企业私仓`
- `市场仓 != 公共储备仓`

## 6. 仓库与三类市场的关系

### 6.1 与标准商品市场

关系最紧密。

标准商品市场天然需要：

- 统一目录
- 统一计量
- 统一托管
- 订单簿撮合
- CLAIMABLE 提取
- 异常恢复

所以标准商品市场必须拥有自己的正式托管仓主链。

### 6.2 与定制商品市场

不应复用标准商品市场仓。

定制商品市场更接近：

- 单件物品托管
- 挂牌快照托管
- 买家待领取 / 卖家待完结

它可以有自己的 `挂牌托管 / 交付托管` 语义，但这不是标准商品市场的 AVAILABLE/CLAIMABLE 模型。

### 6.3 与汇率市场

不应拥有商品仓语义。

汇率市场的核心是：

- 报价
- 限额
- 规则
- 结算

它最多只需要：

- 可兑换资产来源说明
- 兑换执行结果
- 审计与风控字段

而不应共用商品托管仓状态。

## 7. 仓库与企业 / 公共制度的关系

这部分是当前最值得提前预留的地方。

### 7.1 企业玩法

如果后续允许玩家创建企业，那么企业至少可能有三类库存：

- 原料库存
- 成品库存
- 待售库存

其中只有 `待售库存` 进入市场时，才应转入市场托管仓。

也就是说：

- 企业仓是经营库存
- 市场仓是交易库存

两者要可流转，但不能混成同一个概念。

### 7.2 公共 / 政府玩法

如果后续存在公共财政、公共工程或政府收储，则公共侧也应有自己的仓：

- 工程材料储备
- 福利物资池
- 战略储备
- 临时稳定价格的干预储备

这类仓可以：

- 从市场采购
- 向市场释放
- 被公共任务消耗

但它的制度目标与市场盈利逻辑不同，所以不应直接复用玩家企业仓的治理语义。

## 8. v1 页面应该如何理解

虽然这份文档不直接做 GUI，但它会约束后续页面该长成什么样。

`市场仓库 v1` 页面不应该像“说明页”，也不应该像“大箱子列表”。

它更应该像一个资产状态工作台，至少分成下面几块：

- `可交易库存`
- `挂单占用`
- `待领取资产`
- `异常 / 恢复`
- `最近操作记录`

页面重点应是：

- 当前有什么
- 当前能做什么
- 当前为什么不能做
- 最近发生了什么

而不是大段制度说明。

制度说明更适合通过：

- 浮动说明框
- 帮助弹窗
- 风险提示

来承接。

## 9. 建议的数据与制度方向

后续实现时，我建议坚持以下几个方向：

### 9.1 先坚持状态账本，再做花哨交互

最重要的是资产状态可信：

- 来源清楚
- 状态清楚
- 去向清楚
- 恢复路径清楚

### 9.2 任何跨系统流转都必须有“边界转换”

例如：

- 背包 -> 市场仓
- 企业仓 -> 市场仓
- 市场 CLAIMABLE -> 玩家背包
- 市场采购 -> 公共仓

每次转换都应被明确记录，而不是隐式改字段。

### 9.3 不要过早做“统一大仓”

后续也许可以有更上层的“物流 / 集团 / 联邦库存视图”，但那应该建立在：

- 市场仓
- 企业仓
- 公共仓

各自边界都稳定之后。

## 10. 当前建议的实施顺序

建议顺序如下：

1. 先把 `标准商品市场托管仓 v1` 定义清楚
2. 再补它在终端里的正式工作台页面
3. 然后评估 `企业私仓` 是否进入近期路线
4. 最后再讨论 `公共仓 / 政府储备仓` 与公共工程、福利、价格稳定的制度联动

## 11. 当前结论

当前最稳的产品判断是：

- 先把仓库理解成 `受制度约束的资产状态系统`
- 第一版只把 `标准商品市场托管仓` 做扎实
- 企业仓与公共仓必须提前在概念上区分，但不急着在一轮里全实现

如果后续实现还能始终稳定回答下面三个问题，就说明方向还没跑偏：

1. 这批资产当前属于 `谁`
2. 这批资产当前处于 `什么状态`
3. 这批资产当前服务的是 `市场、企业，还是公共制度`

如果回答不清，就说明仓库模型已经开始混了。

## 12. 已落地的定制挂牌交付边界

定制市场不借用标准商品的 `AVAILABLE / ESCROW / CLAIMABLE` 数量账本。它的托管对象是
一份单件 `ItemStack` 快照，状态只描述这件物品的交付位置：

- `ESCROW_HELD`：卖家发布后，物品由定制市场托管；
- `BUYER_PENDING_CLAIM`：买家已完成银行结算，但物品尚待进入背包；
- `COMPLETED`：买家领取成功；
- `CANCELLED`：卖家撤回成功；
- `EXCEPTION`：交付状态需要管理员介入，不允许把它当作普通可领取资产继续重试。

终端发布会先从当前手持槽取走单件物品，再创建挂牌和快照；终端领取或下架通过
`MinecraftCustomMarketDeliveryPort` 做背包容量预检和实际交付，成功后才收口相应状态。
这条交付链与标准市场的可堆叠托管库存保持隔离。

运维应使用 `scripts/market-audit.sh --strict` 同时检查标准市场和定制挂牌。脚本能验证
数据库快照、成交记录和状态组合；它不能替代玩家背包的人工确认。出现
`custom_exception_deliveries` 或关系缺失时，应暂停对相应挂牌的自动操作，先核对审计记录和
玩家背包，再做人工恢复。

## 13. 当前实现映射与下一步

截至 2026-07-19，终端已按本草案分开市场页的库存语义：

- 标准商品市场：数据库正式目录、`AVAILABLE`、卖单 `ESCROW`、买入 `CLAIMABLE` 与银行冻结资金。
- 定制商品市场：单件挂牌、交付与待领取信息，不共用标准品的市场托管余额。
- 汇率市场：正式兑换对、报价、规则和限额，不建立商品托管仓。

跨域转移的详细合同、审计字段与恢复原则见
[`warehouse-transfer-and-audit-boundary-v1.md`](warehouse-transfer-and-audit-boundary-v1.md)。下一阶段不是把三类页面接到同一个“仓库”中，而是先让企业仓、公共仓各自拥有独立的所有权、授权和转移审计规则后再接入。
